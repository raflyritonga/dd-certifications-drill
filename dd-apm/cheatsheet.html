Unified service tagging and primary tags

Exam-heavy

Three reserved tags tie traces, metrics, logs and profiles together. service tracks services, version tracks deployments, env is the mandatory primary tag. Needs Agent 6.19 / 7.19+.

serviceDD_SERVICEOn every span. Links APM to logs, infra and custom metrics; scopes monitors to services
envDD_ENVDefault, mandatory primary tag. Untagged data gets env:none
versionDD_VERSIONMust change with every deploy. Drives Deployment Tracking and Faulty Deployment Detection
Trace metricsNo custom tagsOnly env, service, version, resource, HTTP status, host tags, second primary tag
PlatformHow to set env / service / version
Host processDD_ENV=prod DD_SERVICE=web DD_VERSION=1.2.3 /bin/my-service (or Chef/Ansible into systemd). Agent-level version is not recommended
KubernetesLabels tags.datadoghq.com/env|service|version on both the workload and the pod template, plus DD_ENV/DD_SERVICE/DD_VERSION for APM (downward API or injected by the Admission Controller). Per container: tags.datadoghq.com/<container>.version
DockerEnv vars + labels com.datadoghq.tags.env|service|version. Untraced software (Redis, NGINX): labels only
ECS / Fargateenvironment + dockerLabels on the application container, not the Agent container
OpenTelemetryservice.name → service, service.version → version, deployment.environment.name → env. DD_* vars are not read by OTel SDKs

Primary tags

  • Scope a whole APM app: requests, latency, errors, Apdex, traces. env + one optional second primary tag (datacenter, AZ, cluster, region)
  • Second primary tag: APM Settings, org admins only, up to 2 hours to apply, max 100 values, must be a host or container tag (span tags from the SDK and tag-enrichment tags cannot be primary tags)
  • Changing it hides history aggregated by the old tag; monitors on the old tag go No Data
  • Set env in the SDK. Different env on tracer and Agent = duplicate tags on trace metrics
  • Don't put env or region in service names (prod-web-store); use env / a primary tag

Tags on trace metrics

  • Available: env, service, version, resource, http.status_code, http.status_class, rpc.grpc.status_code (7.65+), Agent host tags, additional primary tags
  • Custom span tags are NOT available on trace metrics. Need them? APM > Generate Metrics (span-based custom metric, 15 months)
  • Monitor linked to a service when service:<name> is in its tags, its query, or the query groups by service
  • Tag rules: start with a letter, max 200 chars, lowercased (span/metric tags), key = text before the first colon (env:staging:east → key env). Avoid unbounded values (user IDs, timestamps).
  • Agent DD_TAGS is space-separated ("test:this is a test" = 4 tags); tracer DD_TAGS is comma-separated key:value.
  • Reserved tag keys: host, device, source, service, env, version, team. The Agent enforces no precedence: one key can carry several values.
  • Peer tags name inferred services (peer.db.name, peer.service, peer.hostname, peer.messaging.destination...). Tag enrichment (Preview, admin) adds team/system from Catalog metadata, not retroactively.

Billing allotments

  • Per APM host per month: 1 million indexed spans (15-day retention) and 150 GB ingested spans, pooled
  • Fargate task: 195,000 indexed / 30 GB ingested. Lambda: 150,000 indexed per 1M invocations
  • Overage: $1.70 per million indexed, $0.10 per GB ingested
  • APM $31, Pro $35 (+ Data Streams), Enterprise $40 (+ Continuous Profiler, 4 profiled containers per host)
  • Intelligent retention filter spans do not count toward indexed usage

Exam traps

  • Postmortem notebook after an incident = trace metrics (they outlive spans)
  • Retention filters never reduce ingested GB; ingestion controls never change trace.* metrics
  • Span-based custom metrics come from ingested spans (indexed or not), names can't start with trace.
  • Data volume limits: spans up to 18 h in the past / 2 h in the future; 30 versions per env+service per 40 min

Tracing libraries and instrumentation types

Exam-heavy

Pipeline: Datadog SDK (tracer) in the app → Datadog Agent (trace-agent, port 8126) → Datadog. Every span has at least a name, start time and duration (plus trace ID, span ID, service, resource). The main reason for distributed tracing: services written in many languages and running on many platforms.

Official vs community tracers

  • Official (Author = Datadog): dd-trace-java, -py, -rb, -go, -js, -php, -dotnet, dd-trace-cpp, Rust SDK. ddprof is a profiler, not a tracer
  • Unsupported language → community tracers (Elixir spandex, Java apm-client, Rust datadog-apm...) maintained by third parties, or OpenTelemetry
  • Any tracer can post to the Agent API: PUT http://localhost:8126/v0.3/traces; times in nanoseconds; name/service ≤ 100 chars, resource ≤ 5000

SDK vs Agent

  • SDK: creates spans, propagates context (datadog,tracecontext,baggage), applies sampling at the root, sends to the Agent
  • Agent: computes trace metrics on 100% of traffic, sets sampling rates (10 traces/s), error/rare samplers, obfuscation, filtering, ships over 443
  • SSI pitfalls: DD_TRACE_ENABLED=false does not stop SSI; Docker needs containers recreated; the Agent's own K8s namespace is not instrumented

Sampling precedence (high to low)

  • 1. Remote sampling rules (resource-based, from the UI)
  • 2. Adaptive sampling rules (monthly volume target, Agent 7.53.0+)
  • 3. Local rules DD_TRACE_SAMPLING_RULES
  • 4. Remote global rate, 5. local global rate
  • 6. Agent rates DD_APM_TARGET_TPS
  • Tracer > Agent, rules > global rate, remote > local. Error/rare samplers are ignored for services with SDK rules

Retention filters

  • Order matters: the first matching filter keeps or drops the span
  • Default filters: Error Default (status:error), App and API Protection, Synthetics, Dynamic Instrumentation Default
  • Span rate only = span-level (retained_by:retention_filter). Add a trace rate = whole trace indexed, usable in Trace Queries
  • Legacy App Analytics filters became retention filters (Oct 20, 2020). "Analyzed spans" = old name for indexed spans

Intelligent retention filter (30 days, free)

  • Diversity sampling on service entry spans: at least one trace per env, service, operation, resource every 15 min; p75, p90, p95 latency spans; representative errors
  • 1% flat sampling: uniform 1% by trace_id, plus traces of 1% of RUM sessions
  • retained_by: diversity_sampling, flat_sampled, retention_filter, trace_retention_filter

Who sees which indexed spans

  • Trace Explorer, dashboards and notebooks: custom and Intelligent filter spans
  • Trace analytics monitors: custom filters only (Intelligent and indirectly indexed spans excluded)
  • Trace Queries: Intelligent filter + trace-level filters
  • Ingestion Control Traffic Breakdown: blue = ingested, gray = not retained by sampling, orange = SDK rate limiter, red = Agent CPU/RAM limit. Sort by Downstream Bytes/s to cut volume.
  • Billed usage metrics: datadog.estimated_usage.apm.ingested_bytes and datadog.estimated_usage.apm.indexed_spans.

Visualizations

  • Flame graph (default): frame width = share of the resource; not a timeline; self time = part with nothing below it; widest frames grouped on the left
  • Thread Timeline: time-based view per thread (goroutine in Go), shows GC/JIT lanes
  • Call graph: each method once; edge thickness = time calling others, node size/color = self time
  • Compare profiles: red = more time in B, green = less, purple = only in A, blue = only in B

Search and correlation

  • Search profiles with facets: Env, Service, Version, Host, Runtime (e.g. env:prod service:movies-api-java)
  • Trace + profiler in the same process are linked automatically: span Profiles tab (formerly code hotspots). Java manual spans must be activated in a scope
  • Endpoint profiling: Per endpoint call stays meaningful when traffic changes
  • Automated Analysis (Insights) flags issues such as GC overhead, lock contention
  • Official practice answer: the profiler "can always be enabled with in-code configuration". Current docs nuance: the env var works for most languages, but Go needs profiler.Start in code (unless built with Orchestrion).

Span attributes (span content) need @. Span tags (host, container) and reserved attributes don't. Facets are not required to search.

Reserved attributes (no @)

  • env, service, operation_name, resource_name, status, trace_id, span_id, timestamp, type, ingestion_reason
  • Need @: @http.status_code, @error.message, @duration (nanoseconds), @span.kind, @base_service
  • Side panel: attributes in the Info/Overview tab, tags in the Infrastructure tab

Trace Queries (whole traces)

  • a && b both, a || b either, a -> b a upstream of b, a => b a direct parent of b, NOT(b)
  • Where: span_count(a):>10, total_span_count:>1000, trace_duration:>5s
  • Up to 50 sample traces; data from the Intelligent filter and trace-level filters
  • Facets (strings) and measures (numbers, with units) are only for the facet panel and aggregation. Trace View span search does not support wildcards.

Error Tracking

An error span becomes an issue only if it has error.type, error.message and error.stack and belongs to a complete trace. No extra SDK or config for APM.

Grouping and states

  • Fingerprint = service + error.type + error.message (numbers, quoted text ignored) + top meaningful stack frame
  • Custom grouping: span tag error.fingerprint
  • States: FOR REVIEW → REVIEWED → RESOLVED, IGNORED, EXCLUDED (stops collection and billing)
  • Auto-resolve after 14 days; recurrence in a newer version = Regression

Around it

  • Samples 30 days, issues 1 year after last activity. No samples shown = spans not kept by a custom retention filter
  • Monitors: New Issue (incl. regressions) or High Impact; multi alert by issue.id
  • Suspect commits need Source Code Integration + GitHub
  • Exception Replay: local variables, Python/Java/.NET/PHP, DD_EXCEPTION_REPLAY_ENABLED
with tracer.trace("throws.an.error") as span:
    raise Exception("Oops!")          # ddtrace sets error.type, error.message, error.stack
span.set_tag("error.fingerprint", "my-custom-grouping")

Troubleshooting with trace search

Spike on the service page → traces behind the graph → filter (status:error, @http.status_code, version) → open a trace → correlated logs, infra, profiles → postmortem notebook on trace metrics.

Correlation

  • Logs: inject trace/span IDs (DD_LOGS_INJECTION), JSON or parsed logs, Trace remapper on dd.trace_id; logs and traces are sampled independently
  • RUM: allowedTracingUrls (formerly allowedTracingOrigins) = the first-party origins the browser app calls; server must allow the tracing headers (CORS)
  • Synthetics: x-datadog-origin: synthetics, traces kept 15 days
  • Watchdog insights in Trace Explorer: error and latency outliers (OUTLIERS facet section)

Missing traces

  • Startup logs (DATADOG TRACER CONFIGURATION), DD_TRACE_DEBUG=true
  • agent status APM section: Receiver: 0.0.0.0:8126
  • Test from the app container: curl http://<agent>:8126/info
  • Agent flare doesn't help if traces never reach the Agent; tracer flare via Remote Config

Anomaly alert conditions

  • Above or below (default), above, below the gray band; window 15 min to 2 weeks
  • Trigger window vs recovery window (keep them equal); "Alert when 100%" = every point anomalous
  • basic: no seasonality. agile: seasonal, adapts to level shifts. robust: seasonal, stable
  • Seasonality hourly / daily / weekly

SLOs

  • Metric-based: good / (good + bad) events, e.g. trace.*.hits and .errors (preferred)
  • Monitor-based: uptime of up to 20 monitors (APM Metric monitors included)
  • Time slice: uptime from a metric condition (e.g. p95 < 1 s) per 1 or 5 min
  • Windows 7, 30, 90 days; error budget = 100% − target; burn rate alerts (30-day: 14.4 over 1h/5m)
  • Linking to services: service:<name> in the monitor's tags, query or group-by → shown on the service page and Service Map.
  • No-data for trace analytics groups: alert when count is below 1. Notification variables: {{service.name}}, {{span.link}}, {{#is_alert}}.
